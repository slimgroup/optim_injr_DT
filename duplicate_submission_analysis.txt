                    重复提交问题完整分析报告

一、问题确认
================================================================================

✓ 确实存在严重的重复提交问题！

证据1: 从sacct记录中发现
  - 发现54个job names有多个job ID（重复提交的证据）
  - 最严重的例子：
    * DT_POF_eps=0.1_s8: 4个job IDs (3116632_8, 3117189_8, 3117637_8, 3119881_8)
    * DT_POF_eps=0.1_s13: 4个job IDs
    * DT_POF_eps=0.1_s19: 4个job IDs
    * ... 还有51个job names有重复
  
  模式分析：
    - 通常每个job name有3-4个job IDs
    - 最早的是CANCELLED+状态（可能是QOS限制被取消）
    - 中间的有COMPLETED状态（成功完成）
    - 最新的有RUNNING状态（当前正在运行）
    - 这说明同一个job被多次提交了

证据2: 从队列中发现
  - 队列中发现12个samples有重复的job names（不同job ID）
  - 例如：DT_POF_eps=0.1_s8 在队列中有12个不同的job ID

证据3: 从final.jld2文件时间戳分析
  - 发现多个cases有可疑的短时间间隔（< 1分钟）
  - 例如：eps=0.001有27个短时间间隔，最短间隔2秒
  - 例如：eps=0.002有24个短时间间隔，最短间隔0秒
  - 这可能表示同一个job被快速重复运行

二、重复提交的原因分析
================================================================================

根本原因1: 脚本检查逻辑的缺陷

问题1.1: grep -q 的局限性
  当前代码: squeue -u $USER | grep -q "${jobname}"
  问题：
    - 如果队列中有多个相同名字的jobs，grep -q 只会返回true一次
    - 但如果队列中没有这个job，就会返回false，导致重复提交
    - 如果之前的jobs被取消了，检查时可能发现不在队列中，导致重复提交

问题1.2: 检查时机的问题（Race Condition）
  提交流程：
    1. 检查 is_completed_or_queued() -> 如果返回false，继续
    2. 执行 sbatch 提交
    3. 等待0.2秒
    4. 再次检查队列
  
  问题：
    - 提交时检查squeue，但jobs可能：
      * 刚完成（还在队列中显示，但很快会消失）
      * 刚被取消（不在队列中）
      * 刚提交（还没出现在队列中，需要时间）
    - 如果检查太快，可能会误判
    - 如果之前的jobs被取消了，检查时可能发现不在队列中

问题1.3: 没有在脚本运行周期内去重
  当前逻辑：
    - 每次调用 is_completed_or_queued() 时都重新检查
    - 如果同一个脚本运行多次，可能会重复提交
    - 如果之前的jobs被取消了，再次运行脚本时会重复提交

根本原因2: 之前的重复提交遗留

问题2.1: 之前的submit_pof_cases_smart.sh的问题
  - 之前的smart脚本使用sacct检查，但sacct有延迟和匹配问题
  - 导致队列中积累了很多重复的jobs
  - 例如：s8有12个重复，说明这个job被重复提交了很多次

问题2.2: 脚本多次运行
  - 如果脚本多次运行，之前的jobs可能已经完成或取消
  - 再次运行时，检查时可能发现不在队列中，导致重复提交

三、从final.jld2文件角度的分析
================================================================================

检查结果：
  ✓ 没有发现同一个sample有多个final.jld2文件（正常，会被覆盖）
  
时间模式分析：
  - 发现多个cases有可疑的短时间间隔（< 1分钟）
  - 这可能表示：
    1. 同一个job被快速重复运行（但最终只保留最后一次结果）
    2. 或者多个samples在同一时间完成（正常情况）

结论：
  - final.jld2文件会被覆盖，所以如果同一个job被重复运行，
    最终只会保留最后一次运行的结果
  - 无法直接从final.jld2文件判断是否有重复运行
  - 但可以通过sacct记录来判断（同一个job name有多个job ID）

四、改进建议
================================================================================

建议1: 改进检查逻辑

1.1 使用更精确的匹配
  当前: squeue -u $USER | grep -q "${jobname}"
  改进: squeue -u $USER -o "%.50j" | grep -w "${jobname}" | wc -l
  
  优势：
    - 使用-w确保完整匹配
    - 可以统计匹配的数量

1.2 添加延迟重试机制
  当前: 提交后等待0.2秒
  改进: 
    - 提交后等待1-2秒
    - 重试检查2-3次
    - 如果job在队列中，确认提交成功

1.3 在脚本运行周期内记录已提交的jobs
  改进:
    - 使用一个临时文件或数组记录已提交的job names
    - 在同一个脚本运行周期内，确保同一个job name只提交一次
    - 即使检查时发现不在队列中，也不重复提交

建议2: 添加去重检查

2.1 提交前检查
  - 在提交前，检查是否已经在本脚本运行周期内提交过
  - 如果是，跳过

2.2 使用job ID跟踪
  - 提交后，记录job ID
  - 如果发现重复的job name，取消旧的job（可选）

建议3: 使用更可靠的检查方法

3.1 优先检查final.jld2（最可靠）
  - 如果文件存在，任务已完成，跳过

3.2 然后检查squeue（快速但可能有race condition）
  - 如果job在队列中，跳过
  - 添加延迟和重试机制

3.3 考虑检查sacct（但要注意延迟）
  - 只在必要时检查sacct
  - 使用较长的历史范围（30天）
  - 检查所有状态（不只是COMPLETED）
