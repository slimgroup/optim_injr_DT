二、发现的问题
================================================================================

1. 重复提交问题
   POF:
   - 452个job names有多个job ID
   - 总共1637个重复job IDs
   - 357个final_#1.jld2备份文件（运行了至少2次）
   - 54个final_#2.jld2备份文件（运行了至少3次）
   - 至少浪费了465次的node hours

   CVaR:
   - 827个job names有多个job ID（比POF更严重！）
   - 280个final_#1.jld2备份文件
   - 至少浪费了280次的node hours

2. 根本原因
   - 没有在脚本运行周期内去重（最重要！）
     * 每次调用is_completed_or_queued()时都重新检查
     * 如果同一个脚本运行多次，可能会重复提交
     * 如果之前的jobs被取消了，再次运行脚本时会重复提交
   
   - Race Condition（竞争条件）
     * 提交时检查squeue，但jobs可能刚完成/刚被取消/刚提交
     * 之前只等待0.2秒，时间太短
   
   - grep匹配不够精确
     * 使用grep -q可能匹配到部分字符串

三、实施的改进
================================================================================

已改进两个脚本：

1. submit_pof_cases_simple.sh
2. submit_20_cases_samples_65_128_smart.sh (CVaR)

关键改进（3个部分）：

改进1: 添加关联数组SUBMITTED_IN_THIS_RUN（最重要！）
  - 位置：在脚本顶部（函数定义之前）声明
  - 代码：declare -A SUBMITTED_IN_THIS_RUN
  - 作用：记录在同一个脚本运行周期内已提交的jobs
  - 保护机制：即使jobs被取消了，也不会在同一个脚本运行周期内重复提交

改进2: 在is_completed_or_queued()/is_submitted()中首先检查SUBMITTED_IN_THIS_RUN
  - 位置：函数开始处，在所有其他检查之前
  - 代码：
    if [[ -n "${SUBMITTED_IN_THIS_RUN[${jobname}]:-}" ]]; then
      return 0
    fi
  - 作用：如果job已经在本脚本运行周期内提交过，直接跳过

改进3: 在submit_one_sample()中提交成功后立即标记
  - 位置：sbatch成功返回job ID后
  - 代码：SUBMITTED_IN_THIS_RUN["${jobname}"]=1
  - 作用：立即标记为已提交，防止后续重复提交

改进4: 改进队列检查逻辑（辅助保护）
  - 使用grep -w确保完整匹配（避免部分匹配）
  - 增加等待时间从0.2秒到1.0秒
  - 添加重试机制（最多2次重试，每次等待0.5秒）

四、为什么这些改进能确保不再重复提交
================================================================================

核心机制：SUBMITTED_IN_THIS_RUN关联数组

工作原理：
1. 脚本开始时，关联数组为空
2. 每次调用is_completed_or_queued()时，首先检查关联数组
3. 如果job name在关联数组中，直接返回"已提交"，跳过所有其他检查
4. 如果job name不在关联数组中，继续检查final.jld2和队列
5. 如果决定提交，执行sbatch
6. sbatch成功后，立即将job name添加到关联数组中
7. 后续如果再次检查同一个job name，步骤2会发现它在关联数组中，直接跳过

关键保护：
- 即使job被取消了（不在队列中）
- 即使final.jld2不存在
- 即使队列检查有race condition
- 同一个job name在同一个脚本运行周期内只会提交一次

为什么之前会重复提交：
- 之前没有关联数组，每次检查都重新查询队列和文件系统
- 如果job被取消了，队列查询返回"不存在"
- 如果final.jld2不存在，文件检查返回"不存在"
- 脚本认为job没有提交，所以再次提交
